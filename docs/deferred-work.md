## Приоритет 1 — надёжность

### [ ] 1. WAL и `busy_timeout` для SQLite
**Проблема.** `make_engine` (`bot/core/db.py`) включает только `PRAGMA foreign_keys=ON`. Диспетчер и `scheduler_loop`
пишут в один файл параллельно (планировщик коммитит после каждого чата при публикации, пользователи в это время
записываются на тренировки) — возможен `database is locked`.

**Что сделать.**
- В `connect`-хуке `make_engine` добавить `PRAGMA journal_mode=WAL` и `PRAGMA busy_timeout=<мс>` (только для sqlite).
- Проверить, что тесты (`tests/conftest.py` ставит `journal_mode=MEMORY`) и конкурентные тесты
  (`tests/participation/`, `tests/inventory/test_service.py`) остаются зелёными.
- Обновить §1 и §8 в `ARCHITECTURE.md`.

**Готово, когда:** прагмы выставляются при каждом соединении, тест на их наличие добавлен, все тесты зелёные.

### [ ] 2. Идемпотентные уведомления в задачах и объявлениях
**Проблема.** `PublishService.send_reminders` (и `announce_cancelled`, `announce_replaced`) рассылают уведомления в
цикле без обработки ошибок. Исключение из `notify` на N-м участнике откатывает задачу `remind_2h`, и на следующем
тике первые N−1 получат напоминание повторно. Это противоречит §9 («обработчики идемпотентны»).

**Что сделать.**
- Перехватывать исключение `notify` на каждого получателя (логировать и продолжать), как это делает
  `_notify_quietly` в `bot/usecases.py`.
- Вынести эту логику в одно общее место (например, обёртка над `Messenger.notify`) и использовать и в
  `usecases.py`, и в `PublishService`.
- Решить, нужна ли отметка «уведомлён» (для строгой идемпотентности повторного запуска всей задачи).
- Тесты: `FakeMessenger`, который падает на одном получателе; остальные получают ровно одно уведомление,
  задача завершается.

**Готово, когда:** сбой доставки одному не приводит ни к повторам другим, ни к повторному запуску задачи.

### [ ] 3. Лимит попыток и статус «failed» для задач очереди
**Проблема.** `run_due_jobs` (`bot/jobs/runner.py`) повторяет упавшую задачу каждые 30 с бесконечно: нет счётчика
попыток, backoff, `last_error`. Постоянно падающая задача засоряет логи и занимает слот из 100 в выборке.

**Что сделать.**
- Добавить в `ScheduledJob` поля `attempts`, `last_error`, `failed_at` (миграция Alembic, §5/§10).
- Backoff между попытками (например, `run_at += min(2**attempts, N) минут`).
- После лимита попыток — пометить задачу failed, исключить из `due_job_ids`, предупредить админов.
- Обновить §9; тесты в `tests/jobs/test_runner.py`.

**Готово, когда:** «ядовитая» задача перестаёт выполняться после лимита, админ уведомлён, остальные задачи не страдают.

## Приоритет 2 — целостность данных

### [ ] 4. Атомарность составных use case'ов
**Проблема.** Сервисы коммитят сами, поэтому use case'ы в `bot/usecases.py` — серии отдельных транзакций.
Пример: `cancel_trainings` — `ScheduleService.cancel` коммитит (`schedule/service.py:206`), затем отдельно
`InventoryService.cancel_for_training` и `announce_cancelled`. Падение между шагами оставляет тренировку отменённой,
а заказы инвентаря активными и без объявления. То же для `update_series`, `decline_training`,
`manual_remove_participant`.

**Что сделать.** Сначала решение (короткий документ в `docs/superpowers/specs/`), затем реализация:
- Вариант A: сервисы делают `flush`, коммитит use case (граница транзакции — на уровне use case).
- Вариант B: оставить коммиты в сервисах, но упорядочить шаги и сделать повтор безопасным
  (идемпотентные «дочистки»).
- Учесть правила §8: проверка и запись лимита остаются одним SQL-оператором, тесты конкурентности зелёные.

**Готово, когда:** принято и описано в `ARCHITECTURE.md` решение; на каждый use case есть тест на сбой посередине.
