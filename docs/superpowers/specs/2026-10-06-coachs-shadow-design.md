# Coach's Shadow: дизайн

Telegram-бот для велоклуба: расписание тренировок, запись участников, заказ инвентаря.
Источник идей: `idea.md`. Язык интерфейса: русский.

## 1. Цель и границы

Один клуб, несколько тренеров, несколько групповых чатов (по одному на уровень).
Бот ведёт регулярные и разовые тренировки, публикует их в чатах за 24 часа до старта,
принимает запись («пойду / не пойду»), показывает список участников всем и подбирает
инвентарь из ограниченного парка по параметрам участника.

**Не входит в MVP:** лист ожидания, очередь на инвентарь, оплата (только поля в модели),
отметка выдачи/возврата инвентаря, статистика посещаемости, экспорт `.ics`, погода, карта,
Mini App, абонементы, дедлайн заказа инвентаря (поле есть, по умолчанию выключено).

## 2. Решения, принятые в брейншторме

- Бот работает и в группах (пост с кнопками), и в личке (профиль, инвентарь, напоминания).
- Лимит мест задаёт тренер вручную, поле необязательное.
- Дедлайна заказа инвентаря нет; настройка заложена, пустое значение = без ограничения.
- Отметки «выдан/возвращён» нет.
- У чата один уровень, но у одного уровня может быть несколько чатов. У тренировки набор уровней; пост публикуется во всех чатах
  с этими уровнями. Запись относится к тренировке, а не к чату: общий список и общий лимит.
- Тренировки регулярные (по шаблону) и разовые. Пост появляется за 24 ч до старта
  (настройка клуба). До публикации запись закрыта; расписание вперёд видно в `/schedule`.
- Отмена одной или нескольких тренировок заранее, в том числе ещё не опубликованных.
- Роли: `admin` → `trainer` → `member`. Тренеры привязаны к чату: в чате несколько тренеров и один главный (`is_lead`).
  Тренер управляет своими тренировками; главный тренер чата ещё и чужими, если все чаты тренировки под его началом (подробнее в разделе 5, «Роли»).
- Стек: Python, aiogram 3, SQLAlchemy 2 async, Alembic, SQLite (позже PostgreSQL).
- Архитектура: один процесс (бот + планировщик), long polling, код по фичам, Telegram за интерфейсом `Messenger` (см. раздел 4).

## 3. Модель данных

**User**: `telegram_id` (PK), имя, `role` (admin/trainer/member), рост (см), размер ноги (EU),
размер шлема (S/M/L), тип шипов своих туфель (none/spd/look/spd_sl), `created_at`.
Профиль необязателен; недостающее спрашивается при заказе инвентаря.

**Level**: `id`, название, порядок. Справочник, ведёт админ.

**Chat**: `chat_id` (PK), название, `level_id` (не уникально: несколько чатов могут иметь один уровень). Привязка командой `/bind_level` в группе.

**ChatTrainer**: `chat_id`, `user_id`, `is_lead`. Уникально по `(chat_id, user_id)`; в чате не больше одного `is_lead = true` (частичный уникальный индекс). Если у чата есть тренеры, главный обязателен.

**TrainingSeries**: тренер, место, тип (интервалы/длительная/техника), описание, лимит
(nullable), правило повторения (дни недели + время; пусто для разовой), дата начала,
дата окончания (nullable), `duration_min`, уровни (`series_level`, many-to-many).

**Training**: `series_id`, `starts_at`, `duration_min`, снимок полей серии (тренер, место,
тип, лимит, описание), уровни (`training_level`), `status` (scheduled/cancelled/done),
`published_at` (nullable). Снимок нужен, чтобы правка серии не меняла уже созданные
тренировки, а правка одной тренировки не затрагивала остальные.

**TrainingPost**: `training_id`, `chat_id`, `message_id`. Все посты тренировки обновляются синхронно.

**Participation**: `training_id`, `user_id`, `status` (going/declined), `updated_at`,
`added_by` (nullable, если записал тренер). Уникально по `(training_id, user_id)`.

**InventoryItem**: конкретная единица парка (например, «Велосипед №7»). `kind`
(bike/pedals/shoes/helmet), метка, параметры (рама и диапазон роста, размер обуви, тип
шипов/педалей, размер шлема), `active`, `price_per_use` (nullable, под оплату).
Диапазоны роста для рам и совместимость шипов хранятся данными, а не в коде.

**InventoryOrder**: `training_id`, `user_id`, `item_id`, `status` (active/cancelled),
`price`, `paid_status` (оба nullable, под оплату).

**Setting** (ключ-значение): окно публикации (24 ч; сам пост в чате служит напоминанием), напоминание в личку записанным (2 ч до старта),
`duration_min` по умолчанию, дедлайн заказа инвентаря (пусто = нет),
`club_timezone` (IANA, например `Europe/Moscow`).

Время: `starts_at` хранится в UTC. Правила повторения («вт и чт в 19:00») вычисляются в
`club_timezone`, чтобы переход на летнее время не сдвигал тренировки; в интерфейсе время
показывается в том же поясе.

**ScheduledJob**: тип (generate/publish/remind_2h/close), `run_at`, `payload`, `done_at`.

**Invite**: токен, роль (trainer), срок (24 ч), кто создал, кем использован.

## 4. Структура кода

Код делится по фичам. В каждой фиче свои модели, сервис и (где нужно) чистая логика;
хендлеры Telegram собраны отдельно и зависят от фич, а не наоборот.

```
bot/
  core/           # config (.env: токен, ADMIN_IDS, часовой пояс), db (engine, сессия),
                  # messenger (протокол Messenger), permissions (функции-политики), texts
  users/          # User, Invite, ChatTrainer; UserService, RoleService
  schedule/       # Level, Chat, TrainingSeries, Training; ScheduleService (генерация, отмена)
  participation/  # Participation; ParticipationService
  inventory/      # InventoryItem, InventoryOrder; InventoryService, matching.py
  publishing/     # TrainingPost; PublishService, рендер карточек и клавиатур
  jobs/           # ScheduledJob, цикл планировщика, обработчики задач
  telegram/       # aiogram: handlers, middleware, FSM-состояния, CallbackData,
                  # адаптер Messenger
  main.py
alembic/          # миграции
tests/            # зеркалит структуру bot/
```

Правила:
- Фичи зависят от `core`; `telegram/` зависит от фич; фичи не импортируют aiogram и `telegram/`.
- Слоя `repo/` нет: сервисы работают с async-сессией напрямую. Сложные запросы (свободные
  единицы на слот, сводка, пересечения) оформляются именованными функциями рядом с сервисом.
- **Messenger** (`core/messenger.py`) — протокол с методами `send`, `edit_post`, `notify`.
  Сервисы получают его через внедрение зависимости. Реализация на aiogram живёт в
  `telegram/`, в тестах подставляется заглушка. Так сервисы, включая `PublishService`,
  проверяются без Telegram.
- **Права** — функции-политики в `core/permissions.py` (например, `can_edit_training(user, training)`),
  их вызывают сами сервисы внутри операции, чтобы проверку нельзя было обойти из хендлера.
- **Подбор инвентаря** — чистая функция в `inventory/matching.py`: на входе профиль,
  кандидаты и занятые единицы, на выходе предложения с пояснениями. Запрос свободных единиц
  отдельно.
- Middleware (`telegram/`) открывает сессию БД и загружает пользователя на каждый апдейт.

Сервисы: `UserService`, `RoleService` (роли, приглашения, тренеры чатов), `ScheduleService`,
`ParticipationService`, `InventoryService`, `PublishService`.

## 5. Основные потоки

### Запись
`join(training_id, user_id)` в одной транзакции: тренировка `scheduled`, опубликована,
не началась. Если участник уже `going`, операция идемпотентна (ответ «Вы уже записаны»,
лимит не проверяется). Иначе лимит не должен быть исчерпан (считаются `going`). Затем
создание/обновление `Participation` и перерисовка постов во всех чатах. При заполненном
лимите ответ «Мест нет», статус не меняется. Отказ (`decline`) освобождает место и отменяет активные заказы
инвентаря этого участника на тренировку, с уведомлением. Гонки закрывает транзакция
(PostgreSQL: блокировка строки тренировки).

### Генерация и публикация
Задача `generate` раз в сутки создаёт тренировки из серий на 4 недели вперёд и планирует
для каждой `publish` (за 24 ч до старта), `remind_2h` и `close` (в момент старта). Пост в чате и есть напоминание за
сутки: он остаётся в чате, отдельного уведомления за 24 ч нет. Тренировка, созданная менее
чем за 24 ч до старта, публикуется сразу.

`publish` отправляет пост в чаты, чей уровень входит в набор тренировки. Для каждого чата
создаётся `TrainingPost`; повторный запуск после частичного сбоя пропускает чаты, где
`TrainingPost` уже есть (идемпотентность по паре `(training_id, chat_id)`). `published_at`
ставится после обработки всех чатов. Если ни одного подходящего чата нет, `published_at` всё
равно ставится (запись работает через `/schedule` в личке), а админу уходит предупреждение.

`remind_2h` отправляется в личку участникам со статусом `going`.

`close` в момент старта переводит тренировку `scheduled` → `done` (отменённые не трогает),
перерисовывает посты во всех чатах без кнопок и с пометкой «Прошла».

**Личные уведомления.** Бот не может написать пользователю, который не запускал его
(`/start`). Если запись пришла из чата от такого пользователя, она принимается, а в ответ
на нажатие показывается алерт «Откройте бота, чтобы получать напоминания» со ссылкой.
Ошибка отправки в личку такому пользователю логируется и не считается сбоем задачи;
сведения об отмене и изменениях он видит в обновлённом посте.

**Правка серии.** Изменения шаблона применяются к будущим тренировкам серии:
- неопубликованные тренировки перегенерируются без уведомлений;
- опубликованные, но не начатые тренировки явно отменяются (как в «Отмене»: пост получает
  «Отменена», записанным уходит уведомление, заказы инвентаря отменяются), и вместо них
  публикуется новая тренировка из обновлённой серии. Записи и заказы не переносятся,
  участники записываются заново. Уведомление отличается от обычной отмены: «Тренировка
  изменена, запишитесь на обновлённую» со ссылкой на новый пост;
- начатые и прошедшие тренировки не меняются.
Правка одной тренировки (а не серии) не затрагивает серию и остальные тренировки.

### Отмена
Тренер или админ выбирает одну или несколько тренировок и подтверждает. Нельзя отменить
начатую или прошедшую тренировку. Статус
`cancelled`, активные заказы инвентаря отменяются, задачи снимаются. Опубликованный пост
обновляется на «Отменена», записанным (`going`) уходит личное уведомление.
Неопубликованные рассылки не вызывают.

### Подбор инвентаря
Вход: кнопка «🚲 Инвентарь» (в группе бот отвечает «Продолжим в личке» со ссылкой
`t.me/bot?start=inv_<training_id>`).
1. Проверки: тренировка `scheduled`, не началась, дедлайн (если задан) не прошёл, участник
   записан (`going`). Если не записан, бот предлагает сначала записаться. Время окончания
   тренировки считается как `starts_at + duration_min`.
   Недостающие параметры профиля спрашиваются только для выбранных позиций.
2. Мультивыбор позиций: велосипед, педали, туфли, шлем.
3. Уточнения: тип педалей; если туфли свои, тип шипов (сохраняется в профиль).
4. `InventoryService.suggest(training, profile, wanted_kinds)` возвращает по позиции:
   точное совпадение, ближайшее с пояснением или «нет в наличии». Из кандидатов исключаются
   единицы, занятые активными заказами на пересекающихся по времени тренировках
   (`a.starts_at < b.ends_at AND b.starts_at < a.ends_at`).
   - Велосипед: рост в диапазоне рамы; иначе ближайшая допустимая рама с подтверждением.
   - Туфли: размер ноги, тип шипов совместим с педалями; иначе ±1 размер.
   - Шлем: размер головы, иначе ближайший.
5. Проверка совместимости набора (педали и туфли из парка должны подходить друг другу).
6. Подтверждение итогом. Затем в транзакции повторная проверка свободы единиц и
   создание `InventoryOrder`. Если единицу забрали, замена подбирается заново только для
   неё. Уже подтверждённые позиции сохраняются.
7. Отмена заказа доступна до старта, единицы освобождаются сразу.
Если подходящего нет: сообщение «Нет в наличии на это время» с ближайшими вариантами или
предложением написать тренеру.

### Роли
Первые админы задаются `ADMIN_IDS` в `.env` и получают роль при старте; их нельзя снять
через бота. `/whoami` показывает свой Telegram ID. Админ назначает тренеров из списка
зарегистрированных (выбор по имени) или одноразовой ссылкой
`t.me/bot?start=trainer_<токен>` (срок 24 ч). Админов назначает только админ, выбором из
списка. Снятая роль тренера: его будущие тренировки остаются и требуют нового тренера
(пока их ведёт админ). Главного тренера чата назначает админ; главный тренер добавляет и убирает остальных тренеров своего чата. Снять главного нельзя без назначения нового.

Если человек имеет роль тренера, но не состоит ни в одном `ChatTrainer`, `/trainer` сообщает:
«Вы тренер, но пока не добавлены ни в один чат. Обратитесь к администратору» и не даёт
создавать тренировки.

**Права на тренировки.** Тренер создаёт тренировки и серии только для уровней своих чатов
(тех, где он в `ChatTrainer`); админ для любых. Тренер правит и отменяет свои тренировки.
Главный тренер чата правит и отменяет чужую тренировку только если **все** чаты, где она
опубликована, находятся под его началом (он главный в каждом из них); иначе только админ.

### Доступ
Пользоваться ботом может только тот, кто состоит хотя бы в одном привязанном чате клуба.
Бот проверяет это через `getChatMember` по всем привязанным чатам при `/start`, при записи
и при заказе инвентаря через личку (результат кэшируется на короткое время). Остальным бот
отвечает «Бот доступен участникам клуба». Админы из `ADMIN_IDS` проверку не проходят.
Нажатие кнопки в посте внутри привязанного чата считается доказательством членства.

### Ручная запись тренером
Тренер (в пределах своих прав) может записать или убрать любого известного боту
пользователя. Ручная запись игнорирует лимит: бот предупреждает «Лимит превышен» и просит
подтверждения, затем записывает с `added_by`. Записанному уходит личное уведомление
(если он запускал бота).

### Планировщик
Цикл раз в 30 с берёт `ScheduledJob` с `run_at <= now` и `done_at IS NULL`. Задачи
идемпотентны (проверка `published_at` и флагов), пропущенное после перезапуска догоняется.

## 6. UX

**Участник (личка):** `/start` (имя; рост, размер ноги и шлема опционально), `/schedule`
(карточки: время, тип, уровни, место, тренер, «Идут N/лимит», кнопки
`✅ Пойду` · `❌ Не пойду` · `🚲 Инвентарь` · `👥 Участники`; у неопубликованных кнопка
«Откроется …»), `/profile`, `/my` (мои записи и заказы).
**Группа:** один пост на тренировку, обновляется через `edit_message`. «Участники» показывает
«Идут (N) … Отказались (M) …»; длинный список уходит в личку.
**Тренер `/trainer`:** мои тренировки (плюс чужие, которые вправе править главный тренер) (изменить, отменить с мультивыбором, записать/убрать
участника), новая серия и разовая тренировка (FSM-форма: тип, место, уровни, день/время
или правило, лимит, описание, подтверждение), сводка по инвентарю
(«Вторник 19:00: велосипеды M×2, L×1; туфли 42×2; шлем M×1», разбивка по участникам).
**Админ `/admin`:** тренеры и админы, приглашения, уровни, привязка чатов, парк инвентаря,
настройки. Админ может всё, что тренер, для любых тренировок.
Принципы: никаких лишних сообщений в группе; короткие структурные callback-данные
(`join:<id>`, `inv:<id>`); права проверяются на сервере; необратимое действие требует
подтверждения.

## 7. Ошибки

- Бот удалён из чата или нет прав: ошибка логируется, чат пропускается, админ получает
  предупреждение, остальные чаты работают.
- Пост удалён вручную: при обновлении публикуется новый, `message_id` обновляется.
- Rate limits Telegram: небольшая задержка между рассылками.
- Недопустимые действия (запись на отменённую/начавшуюся тренировку, чужая тренировка у
  тренера) возвращают понятный ответ без изменения данных.

## 8. Тестирование

- Юнит-тесты сервисов на SQLite in-memory: запись и лимит, отмена с каскадом на заказы,
  генерация из серий, подбор инвентаря (рост/размеры, шипы, пересечения по времени, ближайший
  размер), права, роли и приглашения.
- Тесты планировщика: идемпотентность, догон после «перезапуска» (подмена времени).
- Тесты рендера карточек из данных.
- Несколько интеграционных сценариев хендлеров на моках бота (запись кнопкой, заказ
  инвентаря целиком).
- Миграции Alembic: `upgrade head` на пустой БД.
